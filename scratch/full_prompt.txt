# ConvergeAI  Phase 1.5

## Chat-First Product Architecture, UI Refinement, Navigation & Realtime UX

We are continuing Phase 1.5.

The purpose of this phase is to establish the **usable intermediate product foundation** before V2.

Do not begin V2 collaborative prompt editing yet.

The most important product decision for this phase is:

> **ConvergeAI should feel like a normal modern LLM chat application first, with collaborative/team capabilities layered on top of that experience.**

It should NOT feel like a dashboard application that happens to contain a chatbot.

The user should be able to enter ConvergeAI and immediately understand:

```text
New Chat
Chats
Teams
Current Conversation
AI Configuration
```

Collaboration should become visible when relevant rather than dominating the entire interface.

---

# 1. FIRST: STOP AND AUDIT BEFORE CHANGING THE UI

Do not immediately redesign components.

First inspect the current frontend and backend and determine:

* why New Chat buttons currently do nothing
* why "View All" does not correctly load the chat section
* why login requires username/password to be entered twice
* how routing currently works
* how conversation creation currently works
* how conversations are fetched
* how teams are fetched
* how authentication state is managed
* whether duplicate React components/forms are being rendered
* whether navigation is using inconsistent routes
* whether the frontend is maintaining multiple conflicting representations of chats
* whether the dashboard, team dashboard and conversation pages duplicate functionality
* whether existing WebSocket lifecycle handling conflicts with route changes
* whether conversation creation already exists in the backend but has no usable frontend entry point

Do not fix these by hiding the broken buttons.

Fix the underlying functionality.

---

# 2. PRODUCT MODEL

The conceptual hierarchy should become:

```text
ConvergeAI

 New Chat

 Chats
      Individual conversations
      Team conversations
      Recent conversations

 Teams
      Team Alpha
            members
            conversations
      Team Beta

 Current Conversation
        messages
        participants
        realtime collaboration
        AI configuration
```

The important principle is:

> **Conversation is the primary workspace.**

A team is a context in which conversations can exist.

A collaboration feature is a capability of a conversation.

Do not make the user think they are entering a completely separate "collaboration application."

The design should have:

* collapsible sidebars
* persistent new-chat action
* recent chats
* recent teams

* compact AI configuration control

Both sidebars must be collapsible.

# 4. VERY IMPORTANT: DO NOT CREATE MULTIPLE "NEW CHAT" BUTTONS

There should be one clearly authoritative New Chat action.

Do NOT have:

```text
Left sidebar:
[ New Chat ]

Main dashboard:
[ New Chat ]

Empty chat:
[ New Chat ]

```

if all three are attempting to perform the same action.

The primary New Chat action should live in the left sidebar.

Other contexts may have a contextual action if genuinely useful, but do not duplicate the same control unnecessarily.

If an empty conversation area needs an action, it should trigger the same underlying New Chat flow rather than implementing a second independent mechanism.

Current bug:

Determine whether the cause is:

* duplicate form rendering
* duplicated component
* nested form
* authentication component rendered twice
* React StrictMode incorrectly triggering state logic
* route/layout duplication
* CSS/layout duplication
* incorrect login/signup mode rendering
* duplicated input state
* duplicated authentication provider

Fix the root cause.

Expected login:

```text

         Welcome back

 [_________________________]
```


The authentication form should be a small, rounded application-level modal/card overlay.

The background should communicate the actual product rather than showing a completely separate authentication universe.

This does NOT mean exposing authenticated data.

The underlying chat interface must remain unauthenticated-safe.

* other users' chats
* team information
* private conversation history
* participant information

This is purely a product-entry experience.

# 25. REALTIME LIFECYCLE EVENTS

The WebSocket is not only for chat messages.

It should function as the application's realtime event channel.

Conceptually:

```text
WebSocket

 Message events
 Typing events
 Presence events
 AI streaming events

 Lifecycle events
       Access revoked
       Conversation deleted
       Membership changed
       Team access revoked
       AI configuration changed
       Connection/system state
```

Do not introduce polling for these if WebSockets are already available.

Polling is:

```text
client repeatedly asks:
"Did anything change?"
```

The desired architecture is:

```text
server detects change
        
server immediately sends event
        
client reacts
```

# 26. ACCESS REVOCATION  EXACT UX

Scenario:

Bob has the conversation open.

Alice removes Bob.

Expected:

```text
Alice
 
Backend transaction
 
membership removed
 
server sends access-revocation event
 
Bob's frontend receives event
 
Bob is informed immediately
 
Bob is redirected
```

Bob should see an in-app notification:

```text
Conversation access removed

You no longer have access to this conversation.
```

Then redirect to:

```text
What can I help you with?
```

or the main new-chat state.

The redirect must happen automatically.

Bob must not remain in the inaccessible conversation.

---

# 27. CONVERSATION DELETED WHILE OPEN

Scenario:

Bob is inside Conversation A.

Alice deletes Conversation A.

Expected:

```text

This conversation is no longer available.
```

Then:

```text

```

The frontend must:

* close the WebSocket
* stop accepting events
* clear conversation state
* remove it from recent chats
* navigate away
* prevent sending further messages
* avoid reconnecting to the deleted conversation


# 30. REALTIME EVENT ORDER

Persistent operations must happen first.

Correct:

```text
User action
    
Authentication
    
Authorization
    
Database transaction
    
Commit
    
WebSocket event
    
UI update
```

Do not tell the frontend that something happened before the database confirms it.

---

# 31. SYSTEM EVENTS ARE NOT CHAT MESSAGES

Do not insert lifecycle events into normal conversation history unless explicitly required.

For example:

```text
"Bob has been removed"
```

should be an application notification/event.

It should not automatically become a permanent message authored by "System".

Keep:

```text
persistent conversation messages
```

separate from:

```text
ephemeral/application lifecycle events
```

---
